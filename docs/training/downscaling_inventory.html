Downscaling a MAGiC inventory

Authors

Akash BV

David LeBauer

Published

September 23, 2026

This session takes the output of a magic-ensemble inventory run and turns it into carbon estimates for every crop field, then aggregates to county and state.

The demo bundle covers four Sacramento-San Joaquin Delta counties (Yolo, Solano, Sacramento, Contra Costa) and trains from the first 100 points of the statewide design, which are space filling on their own. The full chain runs in about ten minutes. Statewide numbers are at the end.

NoteScope

The bundle ships data layers for four counties. A statewide run ships all 57 and uses the same four commands – the workflow predicts onto whatever fields the layers contain, so this is a data scope, not a limit of the pipeline.

For the concepts behind all of this – why design points, how the Random Forest is fit, what the covariates are – see Intro to MAGiC Downscaling

This documentation assumes that the steps in Environment setup have been completed. For a new shell, follow its Every new shell instructions. Run all commands below from the downscaling repository root.

Fetch demo data

./magic-downscaling get-demo-data --config example_user_config.yaml
cp demo-data/modelout/demo_config.yaml config.yaml

The bundle holds three things:

  • modelout/ – SIPNET output, 100 design points x 10 ensemble members, 2016-2023, under output_inventory/
  • data/ – field geometry, attributes, covariates and county boundaries for the four demo counties, plus covariates for the design points so the model can train
  • demo_config.yaml – a filled-in config, copied to config.yaml above

Explore CLI layout

Execution is controlled by magic-downscaling and proceeds in four stages: staging inputs, extracting model output, downscaling, and analysis.

./magic-downscaling -h

The commands are defined by the steps section of the workflow manifest:

less downscaling_manifest.yaml

Key points:

  • Each command is a list of steps, each calling one script.
  • All tuning happens through command-line arguments the CLI builds. Scripts never read environment variables for config.
  • A step declares inputs (files), outputs (files) and params (everything else) as {cli_flag: value_key} pairs. The key is the literal flag the script expects.
  • inputs and outputs values must be keys in the manifest’s paths block, all relative to run_dir. That indirection is what lets you move a run without editing a script.
  • params resolve from your config first, then mode_params, then fixed_values.
  • --verbose reports the exact call issued for each step.

Explore configuration file

less config.yaml

Everything you are likely to change lives here:

  • run_dir – where this run writes
  • mode – keep production. The other modes subsample: demo drops to one ensemble member and one year, dev to ten sites. The bundle is already small because of its data scope and does not need truncating as well.
  • management_scenarios – inventory. Must match the output_<scenario>/ directory in the bundle.
  • outputs_to_extract – TotSoilCarb
  • pecan_output_dir, data_layers_dir – where the bundle is
  • n_cores

Prepare inputs

./magic-downscaling prepare --verbose --config config.yaml
  • copies ensemble output and data layers into run_dir, so the run is self-contained and can be archived or moved
  • fails immediately if a scenario in your config has no matching output_<scenario>/ directory, which is the usual sign the config and the ensemble disagree

About 3.5 minutes.

Extract SIPNET output

./magic-downscaling extract --verbose --config config.yaml

SIPNET writes one NetCDF per site, per member, per year at sub-daily resolution. This reads them all, averages to monthly, and writes one long table in EFI format.

ensemble_output.csv as written by extract
rows sites members months variables
96,000 100 10 96 TotSoilCarb

The row count should be exactly sites x members x months x variables. If it is not, something was dropped and it is worth finding out what before going on.

Values here are still in SIPNET units, kg C m-2 for pools. Conversion to Mg C ha-1 happens in the next step. About 4 minutes.

Downscale to fields

./magic-downscaling downscale --verbose --config config.yaml

For each PFT and carbon pool this:

  • takes the design points that ran with that PFT as training data
  • fits one Random Forest per ensemble member, covariates to model output
  • predicts every field of that PFT, converts to reporting units, multiplies by area
  • repeats at the start date so a change over the period can be formed
  • aggregates to county and state

Fitting one forest per member is what carries the ensemble’s parameter uncertainty through to the field level instead of collapsing it to a single number.

Check before you trust it

Two checks decide whether the maps are worth showing anyone.

A Random Forest cannot extrapolate past its training range, so predictions outside the design points’ range mean a broken join or a unit mismatch rather than a discovery.

Out-of-bag R2 says whether the forest learned anything at all:

Negative means the forest does worse than predicting the training mean.
pft model_output members median OOB R2 members < 0
annual crop TotSoilCarb 10 0.411 0
woody perennial crop TotSoilCarb 10 0.309 1

Analyze the result!

./magic-downscaling analyze --verbose --config config.yaml

Writes diagnostics and maps to figures/: county and field maps per PFT and variable, ALE and ICE curves for the strongest predictors, and a variable-importance summary. About 1 minute.

For comparison, the same product from the full 1000-site statewide inventory. This is what a production run delivers; the demo above is the same code on a smaller data scope.

The full inventory

Same four commands. What changes is the config and the machine.

management_scenarios: [inventory]
outputs_to_extract: [TotSoilCarb]
n_cores: 8
pecan_output_dir: /path/to/your/magic-ensemble/output
data_layers_dir: /path/to/statewide/data_layers
Demo (4 counties) Statewide
target fields 22,729 385,234
minimum RAM 16 GB 400 GB
cores used 4 8
download 1.5 GB your own ensemble output
run_dir on disk ~6 GB >100 GB

Wall time depends on the machine, so treat the memory and disk figures as the binding constraints. downscale is the step that sets them: its cost scales with target fields and ensemble members, not with how many design points trained the forest, so a smaller design does not make it cheaper.

Note prepare copies pecan_output_dir into run_dir, so a statewide run needs room for two copies of the ensemble output.

Scenarios

Practice-change scenarios use the same four commands. The difference is that management_scenarios lists several arms, the ensemble output carries one output_<scenario>/ directory per arm, and the analysis adds scenario-minus-baseline comparisons; this session covers the inventory only.
